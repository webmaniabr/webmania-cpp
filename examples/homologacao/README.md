# Exemplo de homologação

[examples/homologacao/run.sh](run.sh) confere o arquivo binário do SDK C com [examples/homologacao/c_archive.py](c_archive.py) antes de extrair qualquer coisa. O arquivo só pode ter diretórios e arquivos regulares, sem link, caminho absoluto ou `..`. O manifesto de todos os arquivos, exceto o README do SDK C (`share/webmania/README.md`), precisa ter o `c_archive_manifest_sha256` de [dependency-lock.json](../../dependency-lock.json). A biblioteca (`c_library_sha256`), o worker nativo (`worker_sha256`), os metadados (`api_metadata_sha256`) e a auditoria de nomes (`wire_audit_sha256`) também precisam ter os digests fixados. O digest do arquivo inteiro (`c_binary_sha256`) não é comparado, porque muda a cada edição do README incluído. Qualquer outra diferença sai com 77 (`C archive differs from the lock`), e só os arquivos conferidos são extraídos. Depois, compila esta facade em diretórios novos somente contra o pacote CMake extraído desse arquivo (`Webmania_DIR`) e executa um exemplo opcional que emite, consulta e cancela documentos **somente em homologação** (`ambiente` 2). Sem `WEBMANIA_LIVE=1` ele imprime `{"result":"blocked"}` e sai com 77, sem rede. Configuração somente por variáveis de ambiente: `WEBMANIA_CONSUMER_KEY`, `WEBMANIA_CONSUMER_SECRET`, `WEBMANIA_ACCESS_TOKEN`, `WEBMANIA_ACCESS_TOKEN_SECRET`, `WEBMANIA_ISSUER_TOKEN`, `WEBMANIA_API1_BASE_URL`, `WEBMANIA_FILES_BASE_URL`, `WEBMANIA_API2_BASE_URL`, `WEBMANIA_LIVE_SCOPE` (`readonly`, `nfe`, `nfse` ou `all`), `WEBMANIA_LIVE_NFE_PAYLOAD` e `WEBMANIA_LIVE_NFSE_PAYLOAD` (arquivos JSON com `ambiente` 2), `WEBMANIA_LIVE_LEDGER` (obrigatória nos escopos `nfe`, `nfse` e `all`: arquivo gravável onde cada documento e cada resultado desconhecido ficam registrados; sem ela o exemplo sai com 77 antes de ler credenciais), `WEBMANIA_LIVE_ALLOWED_HOSTS` (obrigatória: hosts separados por vírgula; toda origem configurada precisa estar na lista, e sem ela o exemplo sai com 77 antes de qualquer rede) e, opcionalmente, `WEBMANIA_LIVE_POLL_ATTEMPTS` (de 1 a 24, padrão 24; só reduz o número de consultas; outro valor sai com 77). A saída é uma linha JSON por passo, com status, resultado e uma referência curta (`sha256` truncado) em vez de identificadores; arquivos aparecem só como tamanho, `sha256` e formato. As consultas depois da emissão e depois do cancelamento são limitadas e esperam 1 s antes da segunda, dobrando até 10 s. O cancelamento só é confirmado por uma consulta com status `cancelado`: enquanto o documento estiver em processamento ou em `processando_cancelamento` ele é consultado de novo; se as consultas acabarem antes, o ledger registra status `unknown` para a operação de cancelamento e o código de saída é 1, sem reenviar o cancelamento. Credenciais, payloads e bytes nunca são impressos. Uma mutação nunca é reenviada: resultado desconhecido encerra com código 1 e fica no ledger para conciliação por consulta.
